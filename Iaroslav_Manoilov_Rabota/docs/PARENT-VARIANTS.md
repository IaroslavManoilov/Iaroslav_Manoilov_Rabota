# Parent и варианты

## Когда объединять

Подтверждена одна серия, общий тип и назначение, различия являются вариантами выбора: размер, объём, цвет, комплектация и т. п. Похожий внешний вид, один бренд или общий поставщик сами по себе недостаточны. Сначала «Проверка линейки»: полный список SKU, источник принадлежности серии, общие признаки, отличия и решение. Не расширять семью на другие модели без подтверждения.

Старый API использовал `variable` для parent, `variant` для дочернего товара и `parent_id` для связи. Проверить текущую схему. Внутренний parent SKU не выдавать за артикул производителя; применять согласованную конвенцию CMS, проверить уникальность. Не угадывать автоматически `<SKU>_parent`, если конвенция не установлена.

## Общие и вариабельные признаки

Общее значение сохранять общим, реально отличающееся отмечать вариабельным согласно UI/API. У каждого варианта своё точное значение; комбинация значений должна однозначно выбирать вариант. Если два SKU имеют одинаковую комбинацию, найти подтверждённый различающий признак или остановить неоднозначное объединение. ID опций брать из актуального справочника, проверить RU/RO/EN и строчную букву. Не создавать вторую глобальную опцию лишь из-за регистра/языка; изменение глобальной опции может затронуть другие товары, учитывать область действия.

Parent: общее название/описание и свойства. Variant: своё название/параметры/логистика; правила хранения переводов и наследования подтвердить на текущей CMS. Не очищать автоматически variant descriptions только потому, что где-то раньше использовали наследование. Общий parent не должен ложно показывать один размер/вес как одинаковый для всех.

## Обновить существующую семью

Найти anchor SKU → parent → полный состав children. Прочитать каждую карточку по ID; сохранить before всех членов и список связей. Сопоставить с исследованием и порученным объёмом. Не терять существующие siblings и не добавлять новые лишь по похожему названию. Все относящиеся карточки preflight до первой записи. Обновить разрешённые поля и проверить каждый ID, родителя, количество и уникальность SKU/комбинаций. Не считать проверку одного parent проверкой семьи.

## Создать новую семью

1. Получить явное поручение создания parent с указанными вариантами; подтвердить серию.
2. Проверить все SKU и внутренний parent code на дубликаты. Уже существующие товары не создавать заново.
3. Подготовить таблицу общих/вариабельных характеристик, полные локализации и логистику всех физических SKU.
4. Проверить текущий UI/контракт создания: создаются ли children внутри parent либо по отдельности, как связываются options/вариабельность, какие поля обязательны. Не выдумывать POST endpoint.
5. Выполнить поддерживаемую последовательность, сразу сохранять parent ID и каждый child ID. При частичном сбое перечитать CMS и продолжить с фактически созданных сущностей; не повторять весь create.
6. Fresh GET parent и всех children, проверить двусторонние связи, полный состав, selectable options, комбинации, локализации, характеристики и логистику. При доступной витрине проверить переключение вариантов, если это не требует публикации.

## Объединить уже существующие simple

Это отдельное изменение структуры. Требуется прямое поручение объединения. Сохранить IDs, SKU, текущие типы, связи и защищённые поля всех товаров. Установить поддерживаемый путь конвертации и сохранения identities. Не удалять и не пересоздавать товары вместо преобразования, не переносить их фото в parent автоматически. Если UI/API при конвертации автоматически меняет медиа, остановить операцию до способа без медиа-изменений либо отдельного явного разрешения пользователя.

Перед финалом проверить: отсутствуют дубликаты, потерянные siblings и orphan variants; каждый child связан с нужным parent, SKU/ID соответствуют checkpoint, существующие protected fields сохранены. Число вариантов равно подтверждённому плану с учётом ранее существовавших членов.
