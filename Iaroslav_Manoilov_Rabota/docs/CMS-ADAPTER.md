# Работа с админкой и API

## Что подтверждено исходниками Windows

На 2026-10-26 старые `universal_worker.py` и `vitra_line_writer.py` содержат следующую схему. Это сведения из исходного кода, а не live-проверка нового аккаунта или гарантия неизменности API:

| Операция | Путь |
|---|---|
| Админка | https://admin.vitra.md |
| API base | https://api.vitra.md |
| Сессия browser credentials | POST /auth/v1/auth/refresh |
| Поиск | GET /commerce/v1/admin/products?perPage=100&page=1&filter%5Bsearch%5D=SKU |
| Карточка по ID | GET /commerce/v1/admin/products/{id} |
| Определения характеристик | GET /commerce/v1/admin/attributes/all |
| Категории | GET /commerce/v1/admin/categories |
| Обновление в старом writer | PUT /commerce/v1/admin/products/{id}/update |

Refresh возвращал `accessToken`, который использовали в Authorization Bearer только внутри браузерного контекста. Не писать token в файл/логи/чат. В новом инструменте auth POST обновляет сессию; все товарные запросы исключительно GET. Сессионная операция не равна записи товара.

Поиск возвращал `data.items` либо `items`, карточка имела `id`, `sku`, `type`, `parent_id`, `variants`, `translations`, `attributes`, `shipping_attributes`. Переводы содержали `value`, `short_description`, `description`, `meta_title`, `meta_keywords`, `meta_description`. Эти поля надо сверять на текущих ответах. Старый writer сопоставлял packaging attributes с `shipping-length`, `shipping-width`, `shipping-height`, `shipping-weight`, нетто — с core `weight`. Не создавать дублирующую характеристику веса вслепую. Единицы и форму payload перепроверить.

## Чтение

`styles/work/cms_read.py` подключается к отдельному локальному Chrome. Требует уже открытой авторизованной вкладки admin. Не создаёт вкладки в чужой сессии и не закрывает браузер. Поиск обрабатывает страницы и раскрывает возможные parent по ID, принимает только точный SKU. Полный снимок сохраняется только в игнорируемой локальной папке; консоль содержит только summary без токенов.

## Запись

Предпочитать доступный поддерживаемый CMS UI/коннектор. Для API-адаптера сначала установить актуальный формат на разрешённой задаче, включая обязательность полей и сохранение медиа при пропуске поля. Нельзя считать partial PUT безопасным только потому, что payload не содержит images. Нельзя отправлять весь GET JSON назад.

Защитить медиа/цены/остатки/статус/бренд/поставщика и структуру вне порученной операции. Сравнить свежий before, подготовить allowlist полей, сохранить checkpoint. Fresh GET после каждого сохранения. Для семьи — проверить всех. Auth failure, timeout и partial writes не скрывать ретраями.

Контракт создания нового simple/parent/variant в рамках этой передачи не установлен. Исследовать UI/официальный контракт либо уже имеющуюся документацию CMS. Не предполагать, что POST на collection и payload update поддерживаются. Пока нет проверенного write-adapter, Codex выполняет явные задачи через доступный UI. Если ни UI, ни подтверждённой записи нет — контент подготовить, сохранение честно оставить pending.

## Почему не перенесены старые executable writers

В источниках обнаружены: Windows clipboard и DPAPI, жёсткий ChatGPT Project ID старого аккаунта, helpers удаления чатов, прежние фото-промпты, не соответствующие отдельному photo-треку. Их перенос как «готовой программы» дал бы ложное ощущение совместимости. Не запускать такие скрипты без ревизии зависимостей, прав и побочных эффектов. Новый репозиторий содержит правила, структуру и новый read-only connector; это не backup всей Windows-папки.
