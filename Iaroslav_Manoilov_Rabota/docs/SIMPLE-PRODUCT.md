# Простой товар: обновление и создание

## Обновить существующий

1. Найти точный SKU и immutable ID, проверить, что это действительно simple, а не скрытый variant.
2. Сохранить before, исследовать точную модель, подготовить RU/RO/EN, характеристики, категорию и четыре логистические группы.
3. Подготовить ограниченный diff без медиа, цен, остатков и статуса; сохранить поддерживаемым способом.
4. Fresh GET по тому же ID; проверить контент и protected fields; записать итог.

Если SKU оказался вариантом, не переводить его в simple: применить правила семьи и явно описать найденную структуру.

## Создать новый simple

Требуется поручение «создай товар», а не только отсутствие результата поиска.

1. Проверить отсутствие точного SKU, в том числе среди variants и на всех относящихся страницах. Ошибку сети не принимать за отсутствие товара.
2. Исследовать и подготовить весь контент до создания.
3. Через текущий UI установить фактически обязательные поля, способ выбора категории и характеристик, допустимый тип simple. При API использовать только проверенный контракт, не копировать PUT payload как POST.
4. Если CMS требует цену/статус/публикацию, для которых пользователь не дал указаний и нет согласованных defaults, запросить только эти значения; не придумывать их. Не публиковать автоматически.
5. Создать один товар, сразу записать возвращённые ID/SKU и факт создания в checkpoint. При timeout сначала проверить точный SKU в CMS, потом решать о повторе. Не создавать дубликат.
6. Прочитать созданную карточку по ID, проверить тип, связи, все языки, характеристики, логистику, категорию и отсутствие лишних медиа. После partial failure продолжать с созданного ID.

Если товар физически относится к подтверждённой семье и пользователь просит вариативную карточку — использовать parent workflow, а не создавать независимые дубли.
