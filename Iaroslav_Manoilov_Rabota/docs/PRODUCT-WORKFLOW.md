# Полный цикл карточки

## 1. Разобрать задачу

Вход: SKU, модель, URL, фото, список или supplier master. Зафиксировать разрешённое действие (обновить/создать/создать семью/объединить/только подготовить) и треки (контент/фото/загрузка). Один код не является разрешением на все операции. После настройки обычное «полный workflow карточки, обнови в CMS» означает выполнение контента до свежей проверки без вмешательства в медиа, цены, остатки и статус.

Создать локальный run в styles/work/product_runs/<UTC>_<SKU>/, состояние in_progress и список ожидаемых SKU. Блокирующие проблемы отмечать отдельно от ошибок инфраструктуры.

## 2. Точно найти текущее состояние

Поиск SKU в CMS, точное сравнение, чтение карточки по ID. Если это variant — прочитать parent и всех siblings по ID. Если CMS ищет variant через parent — раскрыть parent, а не брать частичное совпадение. Обработать страницы результатов. Сохранить before.json с актуальными карточками и связями; без cookie/токенов.

Прочитать текущие категории и definitions/опции характеристик, не придумывать IDs и не создавать дубликаты переводных опций. Типы simple/variable/variant известны из старого кода, но должны быть подтверждены на текущей CMS. Не менять SKU существующего товара ради соответствия исследованию без поручения.

## 3. Исследовать

Производитель → точный паспорт/инструкция/PDF/каталог → официальный поставщик → надёжные продавцы. Открывать фактические страницы, сохранять URLs и происхождение каждого спорного параметра. Проверить, нет ли другой версии модели. Для HENDI Cod produs — артикул, EAN — штрихкод. Фото — источник видимой конструкции, а не доказательство скрытых функций.

В чистом Content-чате подготовить результат по instructions/vitra-product-cards.txt. На семью — один чат с полным составом variants и сравнением. Не вставлять секреты и полные ненужные приватные выгрузки. Сохранить research.json/исходный ответ и источники локально.

## 4. Подготовить контент

RU → RO → EN, эквивалентно по смыслу. Названия: тип + назначение при необходимости + 2–4 главных подтверждённых отличия; без бренда/SKU. Parent — только общие факты; variants — единый синтаксис и свои отличия.

Краткое описание: H3 Преимущества/Avantaje/Advantages, обычно 5–7 содержательных пунктов с точкой с запятой, цель 6; не выдумывать пункты ради количества. Длинное: ровно три H3 из OVERRIDES, абзацы без списков. Подробные применимые характеристики, точная существующая категория, значения опций со строчной буквы с исключениями для обозначений. SEO: Title 50–60 и Description 140–160 символов, программно подсчитать; keywords без переспама. Бренд/модель в SEO только если проверены.

## 5. Логистика

Отдельные размеры товара/нетто/размеры упаковки/брутто для каждого физического SKU. Сначала поиск. Обоснованные оценки разрешены по OVERRIDES, с численным обоснованием, маркировкой и отдельным logistics.json/md. Нет ориентиров — пробел и запрос измерения. Не переносить габариты siblings автоматически и не подменять подтверждённое число.

## 6. Preflight и сохранение

Проверить все языки, точные H3, числа и единицы, категории, разрешение опций и связей, состав семьи, protected fields. Составить diff: конкретные ID и поля, создания отдельно от обновлений. Проверить свежесть before и отсутствие конкурентных изменений. При явном поручении сохранения обычный проверенный diff не требует нового разрешения.

Использовать поддерживаемый UI либо проверенный API. Не запускать исторические скрипты массовой записи. Записывать по checkpoints, сохранять IDs сразу. Для семьи все члены проходят preflight до первой записи. Сбой не компенсировать удалением без разрешения: сохранить прогресс и продолжить безопасно после диагностики.

## 7. Проверить фактический результат

Fresh GET по каждому ID: тип, SKU, parent_id, состав variants, локализованные названия/описания/SEO, опции и признаки вариабельности, категория, логистика. Проверить сохранение защищённых полей и медиа, включая порядок и привязки. UI-only поля дополнительно проверить интерфейсом. Успешный HTTP-ответ или повторение своего payload недостаточны.

Если заказаны фото — проверить каждый файл и визуальное совпадение, согласно отдельному регламенту. Не считать фото обязательным для запроса исключительно контентного трека; не объявлять фото выполненными, если делался только контент.

## 8. Завершить

final-verification.md + receipt с точным результатом и workspace-relative путями. Очередь completed_verified только при выполнении всего заказанного объёма; иначе needs_review/failed с причиной. Финал пользователю: что сделано, ID/ссылки, семья, что проверено, какие значения оценочны и что осталось. Без уверений «всё готово» при непроверенной записи.
